## 3. Ведение проекта и приёмка интерфейса

### GitHub и работа с ветками

`main` — ветка выпуска и ветка по умолчанию. `dev` — интеграционная ветка для всей текущей разработки. Первые `main` и `dev` получают один коммит существующего клиента как исходную точку. Дальше новые задачи начинаются от свежего `origin/dev` в `codex/<задача>`. Следующие задачи с зависимостями начинаются после появления требуемых изменений в `dev`.

На 14 ноября 2026 GitHub уже содержит начальный снимок из 28 файлов, `3500e961ca5e9f05ec2b03e89084351a5902c8ac`. Самостоятельно повторять инициализацию не требуется. `cargo fmt --all -- --check` на снимке завершился с кодом 1, например в `src/attachments.rs`. Закрепи форматирование отдельным коммитом `R00` и повтори проверку. [Начальный снимок](https://github.com/LoonEman1/voxhold-native-rust/commit/3500e961ca5e9f05ec2b03e89084351a5902c8ac)

### Архитектура и порядок подключения

Имена ниже задают места для нового кода. Существующий модуль расширяй на месте, если он уже владеет сценарием. Выноси код из `main.rs` по ходу `R01` и `R02`, когда появляется конкретный потребитель, с сохранением работающих входов. Направление зависимостей — `приложение GPUI → voxhold-api`, `приложение GPUI → voxhold-media → voxhold-api`. API и медиадвижок не знают об окнах и виджетах.

```text
GPUI event → view action → состояние/команда текущей области
                                    ↓
                           фоновая задача / WS / media
                                    ↓
       слабый handle UI ← типизированный результат с областью и поколением
              ↓
        применить к владельцу состояния → notify только меняющегося view
```

| Где | Чем владеет и что вызывает |
| --- | --- |
| `src/main.rs`, `src/app.rs` при выделении | Инициализация GPUI и ресурсов, окно, один долгоживущий Tokio runtime для API, переход `Instance → Login → Workspace`, завершение сессии. Само окно владеет корневой GPUI entity. Рабочий экран создаётся после успешных входа и загрузки списка серверов. |
| `src/auth.rs` (`R01`) | Отдельное представление каждого шага входа, состояние формы и pending, старт операции login. Корень получает `Session` с нормализованным origin, действующим `Client` и ID пользователя после ответа. Пароль живёт только в форме и текущем запросе. |
| `src/workspace/` (`R01/R02`) | Выбранный сервер, ключ текущего чата, доступ/присутствие, router по событиям, состояние видимости панелей, геометрия shell. Раздели `layout` (чистая функция), `view` и состояние сети по мере извлечения. Левый rail, каналы, шапка, участники и overlay читают одну модель текущего контекста. **Ключи областей.** У сессии есть `(нормализованный origin, account_id, session_generation)`. Внутри неё `Channel { server_id, channel_id }` и `Conversation { id }` — разные варианты ключа. Ветка добавляет `root_message_id` к родительскому каналу. Отдельный `access_generation` меняется при событиях доступа, даже если ID не изменились. Идентификатор окна/модалки или `request_id` различает два запроса одного типа в одной области. Черновик зависит от ключа чата. Приватные медиа-ресурсы зависят от аккаунта, прав, версии контента и нужного размера.

**Операция от кнопки до кадра.** Обработчик читает текущий scope и право, выставляет pending для конкретного действия, берёт копию ключа и полезной нагрузки, запускает конечную задачу в фоне. Результат приходит через слабый handle. Сначала сверяются сессия, scope, поколение и `request_id`, затем обновляются данные и снимается pending. При ошибке тот же владелец показывает состояние и действие повтора. При смене области отменяется работа старой области через принадлежащий ей handle/сигнал. Закрытие и отмена идемпотентны. Смена вкладки в действующей сессии сохраняет черновик и разрешённый кеш в пределах бюджета. События `ready`/ACL инвалидируют соответствующие приватные данные до нового снимка. При logout старые результаты отбрасываются и связанные файлы, подписки, временные буферы и media sessions освобождаются.

**Один пример прохода.** Пользователь открывает канал B после канала A. Workspace меняет `ChatKey`, отменяет A-подписку и A-HTTP, выбирает черновик B и показывает начальное состояние B. Единственный контроллер B запрашивает историю и снимок участников. Лента получает `AppliedPage` в UI-потоке, обновляет индекс на страницу, выставляет якорь, вызывает `notify`. Медиа-запросы ставятся по видимости. Поздний ответ A закрывает только ресурсы своего запроса. Изменение ACL B очищает его приватные видимые данные и инициирует авторитетный снимок, даже если пользователь уже смотрит ЛС на том же сервере.

**Границы I/O.** HTTP, WS, декодирование, чтение файлов, переговоры с peer и ожидание завершения worker выполняются вне UI. `render` получает готовые данные и предсказуемо преобразует их в элементы. Видимость может ставить ограниченную задачу в контроллер с dedup, повторное построение кадра идемпотентно. Удалённый HTTP отклоняется, loopback допускается по правилам Rust `AGENTS.md`. Авторизованный запрос и билет остаются в исходном origin, редиректы отклоняются. Диагностика исключает токены, пароли, билеты и тексты приватных сообщений.

#### Модель состояния и события

В начале каждого среза выпиши существующую функцию входа и место, где она меняет видимые данные. Замени там слабое звено. Для синхронных переходов удобно выделять методы, возвращающие изменённое состояние и очередную работу. Общий event bus потребуется только при фактических пересечениях подписок. Для регрессии с порядком событий тестируй метод применения поверх модели без запуска всего окна.

| Данные | Владелец и ключ | Что сбрасывается и что сохраняется |
| --- | --- | --- |
| Авторизация и локальные настройки | Сессия и окно. Сетевой клиент привязан к origin. Тема и ширины — локальный профиль Windows | При logout сессия теряет право писать UI. Остаются настройки оформления и размеры. Отдельный тестовый профиль позволяет сравнивать два клиента. |

Смена сервера отзывает его snapshot и кеши. `ready` инвалидирует старый доступ до перепроверки. |

Для feature state используй состояния, которые нельзя спутать. Например, получение списка различает `Idle`, `Loading`, `Ready(data)` и `Error`. Для обновления подтверждённого списка сохрани data вместе с текущим `refresh`; для приватного ресурса отдели `confirmed_epoch`, который управляет самим правом рендера. Ошибка отдельной операции (`download`, `delete`, `save`) привязана к этому действию или строке. Общий `busy` корневого окна для всех панелей приводит к конфликтам.

У каждой долгой операции выпиши `owner`, `scope`, причины отмены, владелец `pending` и проверка применения. UI решает видимость действий по подтверждённым данным. Backend заново проверяет права. HTTP `401` относится к конкретной сессии, `403/404` — к текущему ресурсу и соответствующей области. `409` трактуй по действию и фактическому ответу. `429` и временные `5xx` включают ограниченный повтор, с отменой на смене контекста. Пользовательский текст бери из Go. Не выводи в ошибки весь URL, raw body и абсолютные пути.

#### Контракт фоновой задачи

1. Снять нормализованные входы на UI thread. Сохранить ID намерения отправки рядом с доменным состоянием.
2. Создать задачу конкретной области и сохранить handle, если её можно отменить. В приложении API-задачи используют общий runtime, media workers остаются у владельца сессии. Для await из GPUI сверить сигнатуру с локальным crate.
3. Получить `Result` с типами результата и типизированной ошибкой. При повторе запроса сохранить idempotency key, если backend поддерживает повтор операции.
4. Применить на UI thread через `WeakEntity` или эквивалент закреплённого GPUI. Для результата от потерявшего связь владельца просто завершить задачу и освободить свои ресурсы.
5. Проверить scope и ID запроса **до** того, как меняются карта pending, cache и UI. Пример регрессии — «старое превью пришло после обновления прав и сняло pending нового запроса».
6. Позвать `notify` один раз при реальном изменении отображаемого состояния. Логика перехода и проверки версии должна быть доступна тесту независимо от `notify`.

Для GPUI практический ориентир — текущие `cx.spawn_in`, `this.update_in`, `Entity` и `ListState` из `src/main.rs`. Чтобы зафиксировать библиотечный вызов, открывай локальный `gpui-0.2.2` в Cargo registry и собери минимальный вызов. У GPUI порядок hit test, explicit focus и жизненный цикл `Task` зависят от версии. [Документация GPUI 0.2.2](https://docs.rs/gpui/0.2.2/gpui/)

Пример результата с проверкой области. Имена типов условные. Используй тот же порядок во всех переносимых callback, в том числе для ошибки и временного файла.

```text
request = {
    operation: LoadOlder, chat_key: active_chat_key,
    session_generation, access_generation, request_id, before
}
history.pending_older = request
await reply = api.messages_page(request.chat_key, request.before)

if active_chat_key != request.chat_key: return
if session_generation or access_generation changed: return
if history.pending_older != request: return

history.pending_older = none
if reply is an error: update_retry_for_this_cursor(reply)
else: apply_older_page_at_current_anchor(reply)
notify_history_if_changed()
```

Закрытие A при ожидающем ответе отменяет тело операции и удаляет его только из старой области. Поэтому возврат из callback B всегда успевает увидеть свой собственный pending. Если операция внешняя и отмена не гарантирует отката (PUT/POST уже на сервере), завершение сверяй по новому подтверждённому снимку или idempotency key. Не скрывай сетевой commit за UI состоянием «отменено» без проверки server outcome.

#### R02.1 · Реальное подключение и порядок событий

WebSocket аккаунта открывается после входа и живёт до выхода или закрытия приложения. При переходе A → B `Client::subscribe_channels` отправляет `channel.unsubscribe` для A и `channel.subscribe` для B по тому же соединению. Без открытого текстового канала сокет продолжает получать серверные события, включая присутствие. После реального разрыва клиент заново выполняет `auth`, ждёт `ready` и восстанавливает подписку на текущий канал. Подтверждения и отказы подписки проверяются по серверу, каналу и поколению доступа. Медиасигнализация принадлежит `VoiceHandle`.

**Зачем это сделано.** При смене канала прежний клиент закрывал WebSocket аккаунта и создавал новый. Backend учитывает присутствие по активным авторизованным соединениям, поэтому веб-клиент второго пользователя мог получить «офлайн», а затем «онлайн». Исправление в [PR #6](https://github.com/LoonEman1/voxhold-native-rust/pull/6), коммит [`8f044d8`](https://github.com/LoonEman1/voxhold-native-rust/commit/8f044d885db2c28732641930bd53ebc6dc6e158d).

**Проверка.** Тест `changing_channels_reuses_the_authenticated_socket` проверяет один `auth`, смену подписки и доставку присутствия после её снятия. На изолированном backend `9b29fdd` второй аккаунт получил «онлайн» при подключении и «офлайн» при отключении. Четыре выбора канала и снятие подписки не породили смены статуса. Для ручной проверки открой участников в вебе под вторым аккаунтом и переключайся между двумя текстовыми каналами в Rust. Статус должен оставаться «В сети» до выхода из клиента.

| Событие | Куда применять и как тестировать |
| --- | --- |
| `ready`, `channel.subscribed`, `channel.sync_required` | Сессия и канал получают новый authoritative pass. Инвалидировать generation доступа до сетевых запросов. При повторном `channel.subscribed` не запускай два совпадающих refresh. |
| `channels.changed`, `channel.created/updated/deleted`, `server.member_*`, `server.deleted` | Обновить область, права, список каналов, участников, кеш и записанный media epoch. Текущие страницы приватной области блокируются до подтверждения. Отзыв закрывает viewer/codec и меню от старой области. |
| `presence.snapshot/updated`, `avatar.updated`, `channel.activity` | Обновить индекс по ID и версию строки, а не весь чат. Activity используется для unread соседних каналов. Собственные события и разрешённая видимость считаются по Go поведению. |
| `message.created/updated/deleted`, `message.reactions_changed`, `channel.read_snapshot`, `channel.read` | Отфильтровать канал, ветку и поколение. Для события до первого GET запомнить bounded merge или отметить authoritative refresh. Revision и `reactions_revision` сравнивать раздельно. Read-id не откатывать назад. |
| `conversation.changed/message/read/deleted`, `recording.updated`, `notification.*` | Передать соответствующей модели. Серверный поток продолжает работу при ЛС. Изменение ЛС не сбрасывает HTTP для записей, а сетевые ошибки уведомлений не закрывают ленту. |

Пусть pending delta событий ограничена известным бюджетом. На overflow сохрани сигнал resync, привязанный к scope. Предотврати окно потерянного сообщения между завершением GET и следующей WS-обработкой. Способ проверки — начать GET с маркером событий, задержать ответ, послать update/delete/insert, закончить GET и проверить итог единственного материала. 401/403/404 должны вести в подтверждённое состояние доступа/ошибки только для применимого scope. Сетевой reconnect использует ограниченный backoff с прерываемым timer, сбрасывает его после стабильного соединения. В UI-обновлении текущий polling `schedule_events` не должен бесконечно запускаться после ухода.

#### R04.2 · Поведение ленты и ошибки действий

- Оставь один обработчик сообщений для двух входов. Превью кнопок в строке не дублируют сетевой код `message_tools`. Меню получает существующий `MessageId`/scope, на клик ещё раз читает текущее состояние, включая права и существование строки. Scope actions и фокус тестируются по `history_actions.go`/`history_selection.go`.
- Выделение многострочного текста идёт через текущие line ranges, emoji и шейпинг GPUI. Сохрани перенос, порядок выделения, а при выборе нескольких строк — порядок Go clipboard. Press по ссылке/цитате и drag выделения дают разные действия. Hover включает часть выступающей полосы быстрых действий, исчезает/меняется после прокрутки. Наличие 2 ссылок одного URL или 2 ответов на одну строку не объединяет идентификаторы наведения.
- Ошибка короткой операции соответствует Go text, остаётся около точки входа. При `403` переоцени текущие права. Не закрывай всё окно из-за ошибки одного действия. При переходе в другой канал очищай контекст попапа. Сохрани pending, retry и подтверждение удаления только если оно ещё относится к видимому сообщению.
- Готовый `R04` проверяется через приложение для каждой операции в Таблице, рукой или сценарным приложением GPUI. Создание/изменение выполняют owner и member там, где это допускает сервер. Для новостей проверь роли publisher и reader, а для поиска — stale page и фальшивый недоступный результат из подменного responder.

**Приёмка.** Для каждой кнопки Go из этого среза зафиксируй реальный вход, результат, негативный вариант по роли и пару кадров. В Go поддерживаются `stream.recovery_request` (SFU) и `stream.p2p_restart`; следуй их точным полям из Go/backend. |
| Завершение | Остановить UI callbacks и frame source, закроется viewer/decoder, voice leave и ICE. Нормальный leave/ошибка транспортов/404 отличаются текстом и действием retry. Отмена локальных задач immediate, ожидание фонового close с таймаутом. После logout у старого lease нет аудио. |

Сверь исходники backend `docs/voice.md`, `docs/streaming.md`, `internal/realtime/http/{handler,stream}.go`, frontend `WorkspacePage.tsx` и `PersistentStreamPlayer.tsx`. Состояние viewer легко покрыть deterministic с таймером: A запущен, ожидается `leaveAck(A)`, пользователь выбирает B и тут же C, приходят ICE/A и offer/B; должен запуститься ровно C. Отдельно проверь `stream.stopped(A)` при активном B, повторную публикацию того же пользователя с новым connection_id, закрытый звонок и `request_id` ошибки. В `R07a` поддержи подтверждённые браузером кодеки и default behavior эталона.

#### R07a.2 · Layout голоса и действия плеера

1. Панель комнаты берёт заголовки, пустое/connecting/connected, карточки участника и трансляции из `voice_room.go`. Просмотр комнаты и активный звонок могут выбираться независимо. Обновление UI запланируй вместе с очередным frame, только при новой `sequence`. При уходе из fullscreen или изменении размера результат масштабирования должен соответствовать текущим `pixels × dpi`. **R07b. Перенеси фактический аудиопуть W02a из локального Go.**

1. Сравни состояние `crates/voxhold-media` с Go `media/src/{voice,capture,dsp,voice_loopback}.rs` и `docs/voice-dsp.md`. Портируй DSP/capture-путь с Rust на Rust отдельным коммитом с указанием исходных хешей, wire enum и диапазонов. 2. Тракт в W02a — Windows capture 48 kHz mono 16 bit → блоки по 10 мс → один APM (NS в auto, AGC по настройке, HPF) → предгейтовый уровень → программный gate в threshold → gain 0–200% и clamp → mute/PTT/deafen/server mute дают тишину и сброс старого буфера → `NativeAudioSource` без дополнительной очереди → Opus. В threshold сверяй нулевой порог, гистерезис ±0,02, hold ~180 мс, attack ~3 мс, release ~60 мс. Поддержи малый bounded PCM buffer и счётчики dropped blocks. Capture, обработка и звук идут при остановленной перерисовке. При fallback на platform ADM передавай точный применённый режим. AEC подтверждается только при реальном render-reference и замере эха. Сверь возможности голосовых контролов с фактическим трактом и знакомыми пользователю состояниями Go.
3. Из Go бери unit fixture с шумом/тоном и тест `threshold_gate_and_auto_noise_survive_opus_round_trip`, проверку смены/ошибки устройства и mute в PCM. В изолированном звонке проверь обе стороны с браузером и опиши слышимый результат, измерь dBFS/RMS, CPU и задержку измеренным методом. По симптомам оптимизируй real-time thread, очередь и буферы. В Go локальный synthetic round trip дал примерно −110,7 dBFS на шуме в threshold, −66,3 в auto, полезный тон −15,4 dBFS. Это ориентир исходного fixture. Rust-результат получи своим прогоном.

#### R07b.1 · Что проверить по PCM

### Как воспроизводить рост памяти

У исходного Go воспроизведён отдельный рост в `gg v0.52.7` на Vulkan. `GPURenderContext.BeginFrame` не осушал список `prevCmdBufs` нужного пути. Отдельный offscreen-прогон одной фигуры на 1440 кадрах приблизительно за 24 с дал `prevCmdBufs` 80 → 1520 и private bytes 378,18 → 418,15 МиБ. После idle/GC список сохранялся. В контрольном прогоне с освобождением достижимых буферов `prevCmdBufs` был ограничен. Стенд — RTX 4070 Ti, NVIDIA `32.0.16.1692`, версии Go из эталона, Vulkan. Это измерение конкретного пути, у оконного режима DX12 и у GPUI собственный профиль. [Upstream-обсуждение gg #545](https://github.com/gogpu/gg/pull/545)

У Rust проверяй четыре режима отдельно. Приложение без действий, повторы активного окна с неизменным размером, drag сплиттера при неизменном размере окна и фактический resize окна. GPU-ресурсы живут по правилам используемого backend. Rust- и C++-память, CPU caches и GPU commitment наблюдаются отдельно. Замени рендер-данные на статический fixture для локализации, если повтор окна показывает похожий наклон даже без API и картинок.

### Данные, прогоны и критерии

Прогон в свежем Windows-процессе release на одну ячейку. Один ПК, эталонная шина GPU, режим оконного питания и refresh rate. ### Поиск конкретной причины при плохом прогоне

1. Подтверди, что график относится к PID нужного клиента, а сервер/браузер/профилировщик снимались отдельно. Сними ряд после входа и после паузы, повтори тем же EXE, сравни elapsed, кадры, CPU и размеры кешей.
2. Отключай по одному фактору в диагностическом варианте. Ровная история без зависимого I/O, те же кадры без картинок, фиксированный layout, одни и те же BMP/SVG/texture IDs, offscreen только rect, idle после фактической подачи кадров. Сравни дельту на 1000 кадров и после освобождения ресурса.
3. Если растут собственные объекты, сгруппируй по месту выделения и владельцу. Типовые места проверки здесь — `Vec<Message>` из `render`, `Window::on_next_frame`, неотменённые GPUI Tasks, `sync_channel` overflow/retry, старые scope keys, lazy-image request maps, unbounded voice queues, `RenderImage` с новым ID каждый кадр.
4. Если private bytes растут при ровных app-счётчиках, посмотри нативный heap и GPU. В GPU считай live ID загруженного изображения, render submissions и retired frames. У нового кадра ресурсы предыдущего можно освобождать после границы, которую гарантирует renderer. Проверяй вариант без текстур и с тремя одинаковыми bounded поверхностями. У C++ WebRTC считай peers, observers, tracks, decoders и capture handles; `Drop` Rust wrapper сам по себе не подтверждает завершение worker.
5. В PR приложи воспроизведение, причину по данным и минимальную правку владельца ресурса. Снова прогони ту же ячейку и сценарий функционального ввода. При несовпадении кадра после оптимизации проходят сначала проверки § 3, затем замер той же сборки.

### R07a · Голос и просмотр текущего Go — журнал PR

Ветка `codex/r07-voice-viewer`, база `origin/dev` `e6c85bf` (merge PR #16);
контракты сверены с backend `9b29fdd6d5dc818b7408e4892b8e68b27d123831`,
frontend `ed7cb00ae12398753a8ef48a5a33b864e20cb04c` и Go
`09c82b983d5d842af0627289655b11c37ae56e1d`.

- `crates/voxhold-media/src/catalog.rs`, `viewer.rs`: детерминированная модель
  просмотра без WebRTC и таймеров. Публикация адресуется
  `(server_id, channel_id, publisher_connection_id)` и номером попытки;
  смена B→C ждёт `stream.left` A (5 с), затем запускает ровно C; offer/ICE
  старой попытки и `stream.stopped(A)` не трогают активный B; `stream.watching`
  принимается только по своему `request_id`; ошибка `native-stream-N`
  сравнивается с `request_start`; reconnect сохраняет выбранную публикацию до
  нового `voice.joined`.
- `runtime.rs`: ограниченные last-value слоты `Requests` (controls, watch,
  stream mute, viewport, local mute), коалесцирующая очередь `Updates`
  (терминальные `Error`/`Left` не сливаются, снимки заменяются), bounded
  `device notice`; отдельный поток кадра забирает и переиспользует буфер,
  кадры не копятся. Leave приоритетнее всего, `leave_stream` сбрасывает
  очередь выбора. Регистрация микрофона закрыта до подтверждённого
  `voice.joined`; `Media::Start` больше не открывает захват.
- `controller.rs`, `voice.rs`: join attempt, server mute, roster по
  `connection_id`, `connections_with_audio` для локального mute; смена
  устройства сначала поднимает новый тракт, при отказе восстанавливает
  прежний индекс и отдаёт `Event::DeviceError`; раз в секунду проверяется
  hot-unplug и выполняется fallback; output gain из настроек применяется к
  трекам комнаты, локальный mute всё равно даёт 0.
- `video.rs`: libyuv пишет BGRA напрямую (`I420ToARGB` на little-endian), UI
  больше не меняет каналы на каждый пиксель; синтетический I420 с
  известными красным/синим проверяет порядок каналов, отсутствие
  вертикального переворота и растяжение при scale.
- `src/voice_room.rs`, `src/voice_panel.rs`, `voice_panel/{view,player}.rs`:
  заголовки/статусы комнаты, карточки участников по сетке Go, индикатор
  речи, roster/badge канала, dock 98 px, порядок действий микрофон → звук →

- `src/app/{voice_ops,voice_tests,realtime,workspace,shell_view,navigation_view}.rs`:

### Что обязательно приложить к PR

```text
Задание и ветка
Base origin/dev и опубликованный SHA
Эталонные Go, Backend и Frontend SHA
Вход пользователя и сценарий до/после
Файлы, владельцы состояния и реальные API/WS действия
Попадание в UI 1:1 с ссылкой на пару кадров и размеры/DPI
Команды и результаты исходников, локального UI и настоящего сервера
Smoke медиа, память и FPS с условиями измерения, если этот срез их меняет
Непроверенные состояния с причиной
Следующее задание и необходимые зависимости
```

Перед сдачей воспроизведи хотя бы один основной путь и одну ошибку через нормальный вход. Regression test для проблем с гонкой должен воспроизводить старый симптом на прежнем поведении. Отдельно проверь `git status --short --branch`, ветку PR, итоговый SHA, отсутствие лишних файлов и наличие фактических артефактов, которые использует отчёт. Ссылки GitHub Actions берутся после push. Каждая ветка должна быть рабочей отправной точкой для следующего `dev`.

### Как передать незавершённую задачу следующему исполнителю

Запиши один компактный блок в PR или в согласованном журнале задачи. Укажи последний подтверждённый checkpoint. Один видимый эффект, который уже можно проверить. Оставшийся конкретный шаг вместе с его файлом/символом. Сохрани ревизию seed и точную команду проверки. Ошибки отдели по слоям (API, модель, UI, устройство/драйвер) с наблюдаемым результатом каждой попытки. Если на машине нет подходящего устройства или GPU, приложи доступную синтетическую проверку и выпиши одну ручную, которую остаётся сделать. Следующий исполнитель запускает этот тест и продолжает с указанного checkpoint.

Пример передачи `R06c`, который уже рисует окно и ожидает `R06d`:

```text
Ветка codex/r06-recordings, commit <SHA>, PR <URL> в dev
Готово: шапка и звонок открывают один recordings dialog, Go кадры 1440×900 и 390×760
Подтверждено: tabs, list/retry/owner ACL на Backend 9b29fdd
Следующее: в действии Download связать ticket API и атомарную Windows запись
Регрессия: задержать билет, сменить сервер, проверить отсутствие применения чужого pending
Проверка: 24 МиБ через реальную скорость стенда, hash файла и 0 .part после отмены
```
