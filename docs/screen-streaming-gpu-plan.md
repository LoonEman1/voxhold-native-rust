# GPU-кодирование и декодирование трансляций на Windows

В настройках приложения можно независимо выбрать ЦП или ГПУ для демонстрации экрана и для просмотра чужих трансляций. По умолчанию клиент пробует видеоблок через штатный API, затем вычислительные шейдеры для форматов без подходящего видеоблока, затем ЦП. Цель GPU-пути — хранить видеокадры в GPU-памяти от захвата до кодировщика и от декодера до отрисовки. Переключатели обновлений переезжают в настройки приложения, а ссылки на PR в карточке изменений отображаются как кликабельные `#54`.

## База и область работ

- Rust `afff49dff8356b3469135b254639e3edc244e2f4` из `origin/dev`. Публикация умеет использовать Media Foundation и `PreEncoded` для подтверждённых конфигураций H.264 и AV1 ([#59](https://github.com/LoonEman1/voxhold-native-rust/pull/59), [#63](https://github.com/LoonEman1/voxhold-native-rust/pull/63)). `screen_capture/windows.rs` и `publisher/engine/frames.rs` передают кадр через CPU-конвертации BGRA → I420 → NV12. В `viewer/codec.rs` проверяется совместимость профиля с WebRTC, а `video.rs` забирает уже декодированные кадры и преобразует их для показа. Отдельного выбора аппаратного декодера в Windows-viewer нет.
- Backend `7f2a418f9e07ce293a06c157a68d603c98706cfd`. Сверены `internal/realtime/http/stream.go` и `internal/stream/manager.go`: `stream.start` принимает четыре кодека, `stream.watch` работает с возможностями зрителя, SFU согласует SDP-профиль и связанные payload RTX. Устройство и способ обработки остаются локальным выбором. [Обработчики](https://github.com/LoonEman1/voxhold-backend/blob/7f2a418f9e07ce293a06c157a68d603c98706cfd/internal/realtime/http/stream.go) · [Кодеки SFU](https://github.com/LoonEman1/voxhold-backend/blob/7f2a418f9e07ce293a06c157a68d603c98706cfd/internal/stream/manager.go)
- Frontend `ed48d171a7cb824b42c394cae1121bcc801ea95d`. Сверены `src/services/stream.ts` и `src/components/StreamSettingsDialog.tsx`. Возможности отправителя и зрителя проверяются отдельно, порядок автоматического выбора — H.264 → VP8 → VP9 → AV1. [Согласование кодеков](https://github.com/LoonEman1/voxhold-frontend/blob/ed48d171a7cb824b42c394cae1121bcc801ea95d/src/services/stream.ts) · [Селектор](https://github.com/LoonEman1/voxhold-frontend/blob/ed48d171a7cb824b42c394cae1121bcc801ea95d/src/components/StreamSettingsDialog.tsx)

Область — Windows x64, монитор или окно, 8-битный SDR в голосовых каналах через SFU. Все четыре кодека, H.264, VP8, VP9 и AV1, должны оставаться доступными для публикации и просмотра в пределах возможностей системы, включая программный путь на ЦП. Цель для GPU — покрыть пробелы аппаратных блоков шейдерами на совместимых NVIDIA, AMD и Intel. Режимы, которые не укладываются в нужное разрешение и FPS на данной карте или драйвере, используют доступный CPU-путь. HDR и P2P идут по отдельным этапам [W12 и W04b](development-plan.md#6-пакет-расширений-после-r07). Голос и системный звук используют свои текущие тракты.

## 1. Общая проверка возможностей и покрытие кодеков

Переиспользовать инвентарь DXGI и фоновый worker из `crates/voxhold-media/src/video_encoder/`. Для каждого адаптера проверять публикацию и просмотр отдельно, по кодеку, профилю, размеру и FPS. Положительный результат требует активации на нужном LUID и обработки контрольных кадров. Кеш учитывать драйвер и поколение устройства. Инвалидировать при изменении состава GPU, обновлении драйвера или отказе устройства. Перед реальной сессией повторно проверять активацию. В UI отдавать снимок с причинами недоступности и отбрасывать устаревшие результаты.

| Кодек | Публикация на GPU | Просмотр на GPU |
| --- | --- | --- |
| H.264 | Довести текущий MFT до входа с D3D11-текстурой. Подтвердить Constrained Baseline `42e0xx`, Annex B, SPS/PPS и IDR при `packetization-mode=1`. | Начать с D3D11/DXVA через Media Foundation. Проверить `42e0xx` и принимаемый SFU legacy `4200xx`. |
| VP8 | Проверить конкретные драйверы и доступные аппаратные API. Для карт без подходящего видеоблока, включая RTX 4070 Ti, исследовать шейдерный кодировщик после VP9. | Проверить D3D11/MFT и при необходимости NVDEC на конкретных GPU. Поддержка кодирования и декодирования проверяется независимо. |
| VP9 | Проверить `profile-id=0` в MFT. Для устройств Intel с VP9 encode проверить oneVPL с D3D-устройством на выбранном адаптере. На RTX 4070 Ti проверить шейдерный кодировщик. | Проверить D3D11/DXVA, при пробеле — NVDEC или AMF на поддерживаемых поколениях. Проверить `profile-id=0` и его отсутствие в SDP. |
| AV1 | Довести текущий MFT для Main SDR до текстурного входа. Проверить sequence header, ключевой кадр и разметку OBU. | Проверить D3D11/DXVA и при необходимости backend производителя. Подтвердить 8-битный `profile=0`. |

Приоритет у Windows API, затем у backend производителя, если он закрывает пробел на подтверждённом оборудовании. Для NVIDIA, AMD и Intel фиксировать проверенные пары «модель и драйвер» по каждой роли. WARP, программный MFT и обработку при неподтверждённом адаптере показывать отдельно от GPU. Наличие API или пункта в списке драйвера не засчитывать как поддержку. [Перечисление MFT по LUID](https://learn.microsoft.com/en-us/windows/win32/api/mfapi/nf-mfapi-mftenum2) · [Матрица NVENC и NVDEC](https://developer.nvidia.com/video-encode-decode-support-matrix) · [Возможности Intel](https://cdrdv2-public.intel.com/819636/819636_Intel_Core_Ultra_Proc_PS_Datasheet__Rev001.pdf) · [Декодеры AMD AMF](https://github.com/GPUOpen-LibrariesAndSDKs/AMF/blob/master/amf/doc/AMF_Video_Decode_API.md)

### Вычислительные шейдеры для форматов без видеоблока

Контрольная карта — RTX 4070 Ti. Для AV1 encode использовать аппаратный MFT на NVENC. Для VP9 decode использовать путь к NVDEC через D3D11/DXVA либо API производителя. Для VP9 encode на этой же карте проверить compute, поскольку профиль отсутствует в NVENC. Настройки и диагностика должны показывать фактический путь отдельно для отправки и просмотра. [Матрица NVIDIA](https://developer.nvidia.com/video-encode-decode-support-matrix)

1. Начать с VP9 Profile 0 на шейдерах D3D11/HLSL, чтобы использовать те же Windows-текстуры захвата. Сначала замерить текущий CPU-кодировщик и перенести распараллеливаемые этапы с наибольшей стоимостью. Кандидаты для кодирования — поиск движения, преобразования и обработка блоков. Для декодирования — компенсация движения, обратные преобразования, реконструкция и фильтрация. Если разбор битового потока или энтропийное кодирование выгоднее оставить на CPU, измерить объём обмена с GPU и показать такой путь как гибридный. [Вычислительные шейдеры D3D11](https://learn.microsoft.com/en-us/windows/win32/direct3d11/direct3d-11-advanced-stages-compute-shader) · [Пример гибридного VP9-кодировщика](https://www.ittiam.com/resource/ittiam-enables-opencl-based-vp9-encode-for-mobile-and-consumer-applications/)
2. Довести прототип до обычного VP9-потока через `PreEncoded`, который без изменений принимают SFU, браузер и CPU-декодер Voxhold. Для шейдерного декодера использовать штатный RTP-приём и сравнить выход с эталонными кадрами. Проверить зависимые кадры, PLI, битрейт, смену размера и синхронизацию потоков. Применить тот же подход к VP8 encode и к пробелам по другим ролям и кодекам из матрицы. Каждый кодек требует своей реализации. Пример полностью шейдерного кодирования и декодирования другого формата есть в FFmpeg. [Шейдерные кодеки FFmpeg](https://www.khronos.org/blog/video-encoding-and-decoding-with-vulkan-compute-shaders-in-ffmpeg) · [Формат и декодирование VP8](https://datatracker.ietf.org/doc/html/rfc6386)
3. Сравнить шейдеры с текущим CPU и с видеоблоком там, где он поддерживает тот же кодек. Проверить 1080p60, текст и движение при сопоставимом битрейте и качестве, простое и нагрузку от игры на той же видеокарте. Измерить время кадра, p95 задержки, пропуски, копирования, загрузку GPU и влияние на FPS игры. Включать шейдеры автоматически только на подтверждённых сочетаниях устройства, формата и качества. Если шейдеры не успевают за потоком, продолжать с тем же кодеком на ЦП. До прохождения этих критериев комбинация остаётся открытой в матрице GPU.

## 2. Полный GPU-тракт публикации

1. В `screen_capture/` провести захват окна и монитора через Windows Graphics Capture в D3D11-текстуру. Проверить выбор источника, системную индикацию, курсор, смену размера и закрытие окна. Привязать захват и кодирование к выбранному устройству, где это возможно. На гибридной системе проверить поддерживаемый перенос между адаптерами, учесть его стоимость. [Windows Graphics Capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)
2. Выполнить масштабирование, ограничение FPS и перевод BGRA → NV12 на GPU. Передавать текстуры в hardware MFT через DXGI device manager либо эквивалентный вход backend производителя. Ограничить число поверхностей и синхронизировать их переиспользование. Если нужен CPU readback/upload, учитывать его как копирование и показывать фактический путь. Собственный предпросмотр должен переиспользовать GPU-кадр. Промежуточный CPU-просмотр, если он нужен до готовности рендера, отдельно измеряется и выключается при скрытом preview.
3. Сохранить `NativeVideoSource::capture_encoded_frame`, согласованный SDP и текущие механизмы RTP/RTCP и звука. Для VP8/VP9 подать полный кадр в согласованной разметке и проверить метаданные ключевого кадра через реальный RTP-путь. Для всех форматов проверить реакцию на PLI, управление битрейтом, монотонные таймстампы, отсутствие накопления кадров и восстановление при потере зависимого кадра. Успех подтверждают работающий backend на выбранном LUID, реальные исходящие кадры и воспроизведение зрителем.
4. Для смены кодека, адаптера или режима во время эфира переиспользовать preflight и текущий `stream.stop` → `stream.start`. Сбой до preflight не затрагивает эфир. При отказе GPU во время работы допускать одну штатную попытку продолжить на ЦП с тем же кодеком в автоматическом режиме. При явно выбранной видеокарте показать причину и предложить действие пользователя. Поздним результатам закрытой попытки не давать возобновить эфир.

## 3. Аппаратный декодер и вывод кадров

1. Сделать технический прототип H.264 через существующий screen viewer. В `libwebrtc 0.4.0` / `webrtc-sys 0.3.53` закреплённый Windows-путь не предоставляет UI способ выбрать D3D11 decoder по LUID. Проверить интеграцию на границе `VideoDecoderFactory` / `VideoDecoder` с настройкой на один peer просмотра. При отсутствии подходящего API добавить минимальный закреплённый Rust/C++ мост для viewer и проверить совместимость со статически слинкованным WebRTC. Предпочесть получение кадров после штатной депакетизации и сохранить jitter buffer, RTX/NACK/PLI, таймстампы, синхронизацию со звуком и текущий жизненный цикл просмотра. Общую фабрику голосовых peers не переключать.
2. Создавать аппаратный decoder под реальный профиль из offer на выбранном адаптере. До `stream.watch` проверять то, что известно из каталога, после offer сверять актуальный профиль и подтверждать обработку первых кадров. Для MFT проверить `MF_SA_D3D11_AWARE`, DXGI manager, выходную поверхность и признак фактической DXVA-обработки. При нехватке MFT рассмотреть непосредственно DXVA или API производителя для нужного профиля. После H.264 добавить AV1, VP9 и VP8 по матрице. [D3D11-декодирование в Media Foundation](https://learn.microsoft.com/en-us/windows/desktop/medfound/supporting-direct3d-11-video-decoding-in-media-foundation)
3. Провести NV12-поверхность от decoder до плеера и PiP через единый слот последнего кадра. Проверить Windows-расширение рендера GPUI 0.2.2, где публичный `paint_surface` ограничен macOS. Выбрать минимальную интеграцию D3D11-текстуры с контролируемым сроком владения до завершения GPU-команд. Проверить коррекцию цвета и диапазона, масштабирование, DPI и обрезку. Промежуточный GPU-decode → CPU-readback → UI может использоваться для прототипа. Полный GPU-путь принимается при выводе в окно и PiP без покадрового readback или upload через ЦП.
4. При потере устройства, смене профиля/размера или устойчивом пропуске срока выдачи кадров использовать ограниченное восстановление. Перейти на CPU для того же потока по автоматической политике или по явной команде при выбранной вручную видеокарте. Запросить ключевой кадр. Если смену декодера нельзя выполнить на месте, использовать штатный цикл `stream.leave` → `stream.watch` с сохранением mute, выбора публикации и положения PiP. При неудаче обоих путей освободить подписку и показать причину. Привязать кадры и метрики к попытке просмотра. Остановка или переход к другому эфиру освобождает peer, decoder, worker и поверхности.

## 4. Выбор в настройках приложения

В разделе «Трансляции» две независимые строки.

| Настройка | Элементы | Значение по умолчанию |
| --- | --- | --- |
| Что использовать при демонстрации экрана | `ЦП / ГПУ`. При ГПУ доступен выбор «Автоматически» или конкретной видеокарты. | `ГПУ → Автоматически` |
| Что использовать при декодировании трансляции | `ЦП / ГПУ`. При ГПУ доступен отдельный выбор «Автоматически» или конкретной видеокарты. | `ГПУ → Автоматически` |

- Режим «ГПУ → Автоматически» перебирает подходящие адаптеры с учётом подтверждённой поддержки формата, близости к устройству захвата или рендера и стоимости копирования. Порядок способов обработки — видеоблок через API, подтверждённые шейдеры, ЦП. При автоматическом выборе кодека внутри каждого способа сохраняется порядок H.264 → VP8 → VP9 → AV1. Явно выбранный кодек сохраняется при смене способа обработки. В режиме «ЦП» используется программный кодек. При недоступной явно выбранной видеокарте показать причину, дать выбрать другую или перейти на ЦП, сохранённый выбор сам не менять.
- Для автоматического декодирования использовать задержку от входа декодера до вывода, долю пропущенных кадров и время копирования. Сначала переключаться после подтверждённой несовместимости, сбоя или нескольких последовательных окон, в которых GPU не выдерживает темп потока и CPU способен его выдержать. Подтвердить CPU короткой пробой на том же формате либо измерениями уже запущенной сессии. Порог и период подобрать на стенде, проверить отсутствие повторных переключений в пределах одной попытки. Возврат к предпочтению GPU — при следующем открытии или после восстановления устройства. Класс или марка видеокарты сами по себе не участвуют в сравнении с ЦП.
- Держать предпочтения на уровне приложения, доступными до открытия пикера и независимо от аккаунта или канала. Для новых и старых конфигов без этих полей применить GPU по умолчанию. Сохранять два выбора адаптера отдельно, различать одинаковые модели и заново проверять соответствие на старте. LUID использовать для привязки в текущей сессии. Пропавший или неоднозначно сопоставленный адаптер показать в настройках, оставив сохранённое предпочтение доступным при возврате устройства.
- Убрать выбор backend и GPU из пикера и параметров своего эфира. Сохранить выбор источника, кодека, качества и звука в `StreamPrefsStore`. Показывать фактический кодек, устройство и причину перехода на CPU в данных активного эфира и просмотра. Изменения в настройках применяются при следующем запуске демонстрации или просмотра. Для текущего сеанса пользователь может применить их через явный перезапуск с существующим preflight. Пикер предварительно проверяет настройки, даже если раздел «Трансляции» в этом запуске ещё не открывали.

- Автотесты. Матрица fake GPU и CPU, два одинаковых адаптера, старая конфигурация, устаревший probe, отказ устройства, ограниченные повторные попытки, отсутствие двойного `stream.start`/`stream.watch`. Для обновлений проверить обе настройки по отдельности, прежний конфиг, ошибку записи и рендер Markdown и старых URL из `notes`. Для ссылок проверить ложный домен, похожий путь и разные номера в одном предложении.
- Windows и живой SFU. На NVIDIA, AMD, Intel iGPU/dGPU и гибридной системе пройти Native ↔ Native и Native ↔ браузер в обе стороны для каждого заявленного кодека, включая звук. Отдельно проверить отсутствие поддерживаемого GPU, RDP/VM, смену разрешения, перегрузку, потерю устройства, reconnect, закрытие и PiP. Для обновлений пройти Setup и portable, ручную проверку и автозагрузку до готового пакета с обоими значениями установки при старте.
- Замеры. При одинаковых источнике, кодеке, разрешении и FPS сравнить CPU и GPU на 1080p60 и, где поддерживается, 4K60. Зафиксировать устройство и драйвер, видеодвижки Video Encode/Decode, число копирований через CPU, долю пропусков, время до первого кадра и p95 задержки до вывода, CPU, GPU, память и A/V drift за 30 минут. Показать результат отдельно для аппаратного кодека и полного текстурного пути. Непройденная комбинация остаётся неподтверждённой.
- Проверки по репозиторию. Перед Cargo проверить общий `target_directory`. Запустить `cargo check --workspace --locked`, подходящие тесты и сборку EXE для ручного прогона. В PR отдельно указать сборку, тесты, ручной запуск, реальный сервер и аппаратную матрицу. Включить затронутые сценарии W04a/W12/W12b в итоговую приёмку [W13](w-workflow.md#финальная-приёмка-w13).
