# Обновления VoxHold

Слой обновлений разделён на три части:

| Компонент | Назначение |
| --- | --- |
| `crates/voxhold-update` | библиотека: манифест, подпись, детерминированный ZIP, дельта, загрузка, staging, применение и откат |
| `crates/voxhold-updater` | маленький helper без GPUI: ждёт завершения клиента и применяет подготовленное обновление |
| `crates/voxhold-release` | CLI для ключей, упаковки, дельт, манифеста и проверки |

UI (иконка, прогресс, отмена, tooltip) подключён в приложении: `src/update.rs`
хранит версию, URL и настройки, `src/app/update_ops.rs` — фоновый контроллер,
`src/app/update_view.rs` — иконку в шапке и панель. Слой остаётся без GPUI.

## Канал и адреса

Один канал беты в закреплённом репозитории:

```text
https://github.com/LoonEman1/voxhold-native-rust/releases/download/beta/latest.json
https://github.com/LoonEman1/voxhold-native-rust/releases/download/beta/latest.json.sig
```

В релизе `beta` находятся `latest.json` и `latest.json.sig`. Манифест
указывает на файлы релиза `v<version>`. В нём доступны Setup, portable ZIP,
опциональная дельта и копия подписанного манифеста.
Токены не используются и не должны требоваться. Разрешён только HTTPS;
исключение — HTTP на `127.0.0.1`, `::1` или `localhost` для локальной приёмки.
URL с query-параметрами разрешены, но в логи и ошибки попадает только
схема/хост/путь (`error::redact_url`).

GitHub публикует версионный релиз после проверки загруженных файлов. Затем
CI обновляет подпись канала и `latest.json`. Старые URL пакетов продолжают
отдавать те же байты, поэтому начатую загрузку можно закончить после выхода
следующей версии.

## Схема `latest.json` (schema 1)

```json
{
  "schema": 1,
  "channel": "beta",
  "version": "0.2.0",
  "min_windows": "10.0.19041",
  "published_at": "2026-11-19T12:00:00Z",
  "notes": "Что изменилось",
  "authenticode": true,
  "full": {
    "url": "https://github.com/.../v0.2.0/VoxHold-portable.zip",
    "size": 12345678,
    "sha256": "<sha256 zip>",
    "package_sha256": "<sha256 zip>"
  },
  "setup": {
    "url": "https://github.com/.../v0.2.0/VoxHold-Setup.exe",
    "size": 2345678,
    "sha256": "<sha256 setup>"
  },
  "deltas": [
    {
      "from_version": "0.1.0",
      "from_package_sha256": "<sha256 base zip>",
      "url": "https://github.com/.../v0.2.0/VoxHold-delta-0.1.0.zip",
      "size": 345678,
      "sha256": "<sha256 delta zip>"
    }
  ]
}
```

Проверки:

* `schema == 1`, `channel` совпадает с ожидаемым, `version` — semver;
* `min_windows` — `major.minor.build`; текущая сборка читается из реестра
  (`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion`);
* `published_at` — строгий RFC 3339: календарная дата проверяется по месяцам
  и високосным годам (`2026-02-31` отклоняется), часы `00–23`, минуты и
  секунды `00–59` (секунда `60` запрещена), смещение `Z` или `±HH:MM` с
  `HH <= 23` и `MM <= 59`; смещение нормализуется в UTC;
* `notes` не больше 64 КиБ, дельт не больше 32, размеры не больше 2 ГиБ;
* `sha256`/`package_sha256` — 64 символа нижнего регистра hex;
* для schema 1 `full.sha256` обязан совпадать с `full.package_sha256`:
  скачиваемый portable ZIP — это и есть канонический пакет, второй хэш
  описывает тот же файл;
* URL: HTTPS, либо HTTP только для loopback; логин/пароль в URL запрещены;
* неизвестные поля JSON отклоняются;
* понижение версии — ошибка `Downgrade`, равная версия — `UpToDate`;
* дельта выбирается только при совпадении `from_version` и
  `from_package_sha256` и только если её размер меньше полного пакета.

## Подпись

`latest.json.sig` — Ed25519-подпись сырых байтов `latest.json` в base64.
Подпись проверяется **до** разбора JSON: подделанный или чужой манифест не
попадает в парсер. `check::check_signed_manifest` скачивает `latest.json` и
`latest.json.sig` (HTTPS, лимит 1 МиБ/8 КиБ, отмена), проверяет подпись и
возвращает `VerifiedManifest`.

`VerifiedManifest` — единственный тип, который принимает
`stage::stage_update`; его конструктор доступен только внутри библиотеки и
вызывается из `check_signed_manifest`/`verify::verify_and_parse`. Поэтому
подготовить обновление из неподписанного `Manifest` нельзя: релизный CLI
создаёт и подписывает `Manifest`, а клиент работает только с проверенным
значением. `Deref` даёт доступ к полям и методам манифеста.

Публичный ключ встроен в клиент:

* файл `crates/voxhold-update/update-pubkey.txt` (32 байта, base64);
* либо build-time переменная `VOXHOLD_UPDATE_PUBKEY` — для локальной приёмки.

Приватный ключ канала `beta` создан этой задачей и хранится **вне
репозитория** (точный путь передан в отчёте о выполнении и не коммитится).

В CI он задаётся секретом `VOXHOLD_UPDATE_SIGNING_KEY` (base64 PKCS#8).
`voxhold-release keygen --out <file>` печатает публичный ключ и создаёт пару.

Ротация: выпустить клиент с новым публичным ключом, затем начать подписывать
манифесты новым ключом. Схема v1 хранит один ключ, поэтому период, когда
старые клиенты ещё работают, нужно покрыть отдельным релизом; старые подписи
не переиспользуются.

## Интеграция в приложение

Жизненный цикл обновления принадлежит процессу, а не сессии. Приложение
проверяет манифест через 3 секунды после старта и далее раз в 6 часов, пока
процесс жив. Вход в аккаунт, смена сервера и открытие панели не создают
дополнительных таймеров: панель показывает текущее состояние, а кнопка
«Проверить» запускает проверку вручную. Пока проверка, загрузка или
подготовка уже идёт, повторный вызов ничего не запускает, и панель с кнопкой
показывают текущую фазу.

Настройки хранятся в `%APPDATA%\Voxhold\update-prefs.json`:

```json
{
  "declined_version": "0.2.0",
  "auto_download": true,
  "install_on_next_start": true
}
```

Оба переключателя по умолчанию включены. Старый файл только с
`declined_version` читается как `auto_download: true`,
`install_on_next_start: true`; отсутствие файла даёт те же значения. Каждое
изменение (пропуск версии или клик по переключателю) перезаписывает документ
целиком и атомарно, поэтому `declined_version` не теряется.

После успешной проверки и перехода в `Available` при `auto_download: true`
загрузка стартует сама, если версия не пропущена и не была отменена в этом
запуске. Автозагрузка выполняется не более одного раза на версию за процесс
и использует тот же `stage_update`, что и кнопка «Скачать» (дельта, проверки
хэшей, fallback на полный пакет). «Отмена» останавливает загрузку, возвращает
`Available` и подавляет автозапуск этой версии до следующего старта процесса;
ручная «Скачать» после отмены работает. «Пропустить версию» сохраняет выбор
между запусками и не предлагает версию снова.

Закрытие панели и выход из аккаунта (`end_update_session` из
`src/app/session.rs`) не отменяют ни проверку, ни загрузку и не сбрасывают
готовый `ready.json`. Поколение (`generation`) по-прежнему отбрасывает
устаревшие ответы новых ручных проверок, но logout его не увеличивает.

Фазы панели: `Checking`, `Downloading` (проценты по фактически скачанным
байтам), `Preparing` («Проверяем и готовим обновление…» — хэширование и
распаковка после загрузки) и `Ready`. Фазу сообщает сама библиотека, а не
счётчики байтов: если дельта не прошла после скачивания, `stage_update`
переходит на полный пакет и снова объявляет `Downloading` с новым `total`.
Поэтому проценты продолжаются на полном пакете, а «Отмена» доступна и в
`Downloading`, и в `Preparing` (она останавливает fallback и удаляет
недокачанный файл). В `Ready` текст зависит от
`install_on_next_start`: «Установится при следующем запуске» или «Готово к
установке». Переключатели «Скачивать обновления в фоне» и «Устанавливать при
следующем запуске» видны во всех фазах.

Автоустановка на следующем запуске появится в этапе U2. Текущий U1 только
сохраняет выбор `install_on_next_start` и показывает соответствующий статус в
`Ready`; сам запуск helper'а при старте процесса в U1 не выполняется.

Найденный при старте `ready.json` более новой версии показывается как
«готово к установке» и не применяется молча. После записи handshake
приложение через ~10 секунд повторяет очистку, чтобы удалить каталог уже
завершившегося helper'а.

Локальная приёмка может задать `VOXHOLD_UPDATE_BASE` (loopback HTTP или HTTPS);
подпись манифеста проверяется всегда. Версия сборки берётся из
`VOXHOLD_BUILD_VERSION`, иначе из `CARGO_PKG_VERSION`. Переменные объявлены в
корневом `build.rs` и в `crates/voxhold-update/build.rs`, поэтому смена ключа
или версии пересобирает нужный crate.

## Детерминированный пакет

`VoxHold-portable.zip` собирается `voxhold-release pack`:

* файлы идут в лексикографическом порядке путей;
* фиксированное время 1980-01-01, без extra fields и directory entries;
* фиксированный уровень Deflate, unix mode 0644;
* внутри `package.json`:

```json
{"version":"0.2.0","files":[{"path":"Voxhold.exe","size":123,"sha256":"..."}]}
```

`package.json` не перечисляет сам себя. `sha256(zip)` — это `package_sha256`.
`repack_installed(dir, package_json)` собирает тот же ZIP из установленных
файлов без хранения копии пакета; хэш обязан совпасть с базовым. Установщик
кладёт тот же `package.json` в каталог установки, поэтому дельта работает и
после Setup, и после распаковки portable ZIP.
Детерминизм обеспечивает закреплённая версия `zip 9.5.1`; обновление
зависимости требует пересборки базовых пакетов канала.

Пути внутри пакета проверяются строго: запрещены абсолютные пути, `..`,
обратные слэши и `:`; имена устройств Windows (`CON`, `PRN`, `AUX`, `NUL`,
`COM1..9`, `LPT1..9`) в любом регистре и с расширением; компоненты с
хвостовой точкой или пробелом; совпадения путей без учёта регистра
(`A.exe`/`a.exe`), иначе Windows перезаписал бы один файл другим. Те же
правила применяются к записям дельта-архива.

## Дельта

`delta.json` внутри delta-ZIP:

```json
{
  "schema": 1,
  "from_version": "0.1.0",
  "to_version": "0.2.0",
  "base_package_sha256": "...",
  "target_package_sha256": "...",
  "deletes": ["old/file"],
  "files": [
    {"path": "Voxhold.exe", "mode": "patch", "size": 123,
     "sha256": "...", "patch": {"base_size": 100, "base_sha256": "..."}},
    {"path": "README.md", "mode": "replace", "size": 10, "sha256": "..."},
    {"path": "assets/icon.svg", "mode": "copy", "size": 20, "sha256": "..."}
  ]
}
```

* `copy` — файл берётся из базового пакета;
* `replace` — полный файл лежит в `files/<path>`;
* `patch` — блочный патч лежит в `patches/<path>` (блоки 4 КиБ,
  операции copy/literal); применяется только если он меньше замены.

После применения SHA-256 восстановленного ZIP обязан совпасть с
`target_package_sha256`, иначе `DeltaTargetMismatch`. Если базы нет, хэш базы
не совпал, дельта сломана или дельта не меньше полного пакета — клиент
скачивает полный пакет (`FullFallback`).

## Загрузка и staging

Корень: `%LOCALAPPDATA%\VoxHold\updates` (`$XDG_CACHE_HOME/voxhold/updates`,
иначе `$HOME/.cache/voxhold/updates` вне Windows). Если `LOCALAPPDATA` (или
`XDG_CACHE_HOME`/`HOME`) не задан, `stage::updates_root()` возвращает
`InvalidArgument`; общий `%TEMP%` не используется. Каталог создаётся с
наследованием ACL текущего пользователя; отдельная установка DACL в этой
версии не выполняется. Каталог версии:

```text
updates\<version>\
  package.zip        полный или восстановленный пакет
  delta.zip          скачанная дельта
  app\               распакованная следующая версия + package.json
  ready.json         version, package_sha256, install_dir, created_at, method
  helper.exe         копия helper после self-relocate (может остаться)
  apply.log          пишет helper (пути и коды, без URL)
```

Скачивание:

* только HTTPS (loopback HTTP — для тестов);
* лимит `size + 1 МиБ`, проверка `Content-Length` и фактических байтов;
* `.part` и `Range: bytes=<offset>-`; ответ 206 проверяется по
  `Content-Range`, ответ 200 начинает загрузку заново;
* отмена через `CancelToken`;
* SHA-256 проверяется после завершения; при несовпадении, отмене или
  превышении размера `.part` удаляется; при сетевом обрыве `.part`
  сохраняется для продолжения;
* URL в ошибках — без query и учётных данных.

Память:

* полный пакет проверяется и распаковывается через один открытый файл:
  `package::unpack_file_verified` считает SHA-256 по тому же handle, затем
  делает `seek(0)` и передаёт его в `ZipArchive`, поэтому файл нельзя
  подменить между проверкой хэша и распаковкой. Каждая запись потоково
  пишется во временный файл рядом с целевым, SHA-256 и размер считаются по
  ходу копирования, и только после проверки файл атомарно переименовывается.
  Архив целиком в память не читается;
* в дельте базовый `PackedPackage` перемещается в blocking-задачу, без
  `bytes.clone()`;
* замер (`cargo test -p voxhold-update --locked memory_probe -- --ignored
  --nocapture`, `VOXHOLD_MEMORY_CASE=full|legacy|delta`). ZIP берётся из
  `VOXHOLD_MEMORY_ZIP`, иначе из `%USERPROFILE%\Downloads\VoxHold-portable.zip`
  (`$HOME` вне Windows); без файла замер завершается понятной ошибкой. На
  `VoxHold-portable.zip` 23 077 581 байт: прежний путь (`std::fs::read` +
  `unpack`) — 30.0 МиБ пикового working set и 23.3 МиБ peak pagefile, новый
  полный путь — 12.8 МиБ и 4.3 МиБ. Синтетическая дельта (база 8 МиБ,
  дельта 771 байт) — 36.8–36.9 МиБ working set и 35.3–36.1 МиБ pagefile;
  база и целевой ZIP в этом замере синтетические, а не релизные. Повторные
  прогоны дают разброс около ±1 МиБ (полный путь — 12.7–12.8 МиБ working
  set, дельта — 36.2–37.1 МиБ working set и 35.3–36.1 МиБ pagefile),
  поэтому числа — ориентир, а не точная норма. Замеры сделаны на отладочной
  сборке без оптимизаций и зависят от машины.

Очистка:

* `stage_update` удаляет каталог версии при любой ошибке;
* сетевой обрыв повторяется один раз (`Range`, всего две попытки), затем
  каталог удаляется;
* `cleanup_stale(&root, keep) -> Result<usize>`, где `root = updates_root()?`,
  на старте удаляет старые попытки и посторонние файлы; `updates_root()`
  возвращает `Result<PathBuf>` (`InvalidArgument`, если не задан
  `LOCALAPPDATA`/`XDG_CACHE_HOME`/`HOME`), поэтому корень получают до вызова
  и передают ссылкой. `keep` — `Some(version)` для каталога версии, готовой к
  установке, иначе `None`;
* очистка best-effort по записям: ошибка отдельной записи (занятый
  `helper.exe`, файл, удерживаемый другим процессом) не прерывает проход —
  запись пропускается, остальные удаляются, а возвращается число реально
  удалённых записей. `Err` возможен только если не читается сам корень.
  Пропущенное повторяется при следующем вызове;
* `cleanup_after_install(staging)` удаляет каталог после успешного
  применения;
* helper после успешного применения тоже вызывает best-effort
  `cleanup_stale`: свой образ он удалить не может, поэтому собственный
  каталог версии (`helper.exe` и `apply.log`) не трогает, а убирает
  остальные каталоги версий;
* в обычном случае `updates\<version>` после успешной установки, отмены и
  ошибки подготовки не остаётся. Если ошибка произошла при применении, helper
  оставляет `apply.log` (и каталог версии) для диагностики; следующий старт
  удаляет их через `cleanup_stale`. Если helper был скопирован в каталог
  версии, после успеха он удаляет `app`, пакеты и `ready.json`, но оставляет
  `helper.exe` и `apply.log` — работающий образ нельзя удалить на Windows.
  Этот остаток удаляет приложение: при следующем старте или повторным
  `cleanup_stale` по таймеру после handshake. Пока helper ещё жив, его
  каталог просто пропускается без ошибки.

`apply_staged` меняет установку только через одно durable-состояние
`<install>.voxhold-state.json`. Перед первым переименованием в нём
записываются уникальный id операции (`uuid`), стадия, точные пути staging,
backup и handshake. Стадии: `prepared` (новый каталог собран и проверен,
старый не тронут), `old-renamed`, `new-in-place`, `completed`, `rolling-back`.
`ApplyOutcome.backup_removed == false` значит, что бэкап был занят и остался:
состояние `completed` сохраняется до следующего прохода восстановления.
Коды helper: `0` — успех, `2` — аргументы, `3` — клиент не завершился,
`4` — ошибка применения. В release-сборке helper собран с
`windows_subsystem = "windows"`, поэтому консоль не мигает; ошибки попадают в
`apply.log`/`helper-usage.log` и в код возврата.

## Применение и откат

`voxhold-updater`:

```text
voxhold-updater --pid <pid> --target <install dir> --staged <updates\version> \
  --exe Voxhold.exe --handshake <file> [--detached]
```

`--target`, `--staged` и `--handshake` обязаны быть абсолютными путями;
`--target` и `--staged` должны существовать и канонизируются до смены
рабочего каталога. `--exe` — только имя файла внутри `staged\app`.

0. Если helper запущен из каталога установки или из `staged\app`, он
   копирует себя в `<staged>\helper.exe` и перезапускается оттуда с
   `--detached`; родитель сразу выходит. Windows не даёт переименовать
   каталог с работающим образом, поэтому без этого шага бэкап оставался бы
   навсегда. При старте helper вызывает
   `recovery::recover_install(target, RecoveryMode::Updater)` и сначала
   доводит до конца прошлую операцию, если она ещё не разрешена. Код
   возврата родителя (`0`) означает только успешную передачу управления:
   признак установки — handshake нового клиента, а не выход helper.

   `--detached` — внутренний флаг helper'а: приложение его не передаёт и не
   должно передавать. Флаг добавляет только сам helper при перезапуске
   скопированного образа; запуск с `--detached` из каталога установки или
   `staged\app` helper отклоняет с кодом `4` (иначе он работал бы из
   каталога, который сам же переименовывает).
1. Ждёт завершения PID (до 300 с).
2. `apply_staged` сначала разрешает прошлую операцию тем же
   `recover_install`. Новую операцию можно начать после `Clean`, `Completed`
   или `RolledBack`; `Corrupt`, `NeedsUpdater` и `Ambiguous` с оставшимся
   файлом состояния отказывают и оставляют бэкап. Неизвестный legacy-бэкап
   без файла состояния не блокирует обновление. Доказанный `Completed` тоже
   не блокирует: состояние снимается, старый бэкап остаётся неизвестным
   legacy-каталогом, а новая операция получает собственный
   `<name>.voxhold-backup-<id>` и никогда его не перезаписывает.
3. Копирует только пути из нового `package.json` в
   `<name>.voxhold-next-<id>` на том же томе; файлы пользователя вне пакета
   переносятся туда же. После проверки хэшей записывается состояние
   `prepared`.
4. Переименовывает старый каталог в `<name>.voxhold-backup` (или в
   per-operation имя, если канонический путь уже занят), сохраняет
   `old-renamed`, переименовывает staging в каталог установки и сохраняет
   `new-in-place`.
5. Запускает новый `Voxhold.exe` с `--update-handshake <file>` и
   `--update-operation <id>`. Handshake действителен только для этого id.
6. Ждёт handshake 30 с. Успех — состояние `completed` записывается до
   удаления бэкапа, затем helper пытается удалить бэкап и возвращает
   `ApplyOutcome { backup_removed }`. Ошибка/таймаут — откат: неудачный
   каталог переименовывается в `<name>.voxhold-failed-<id>`, бэкап
   атомарно возвращается на место установки, и только после этого неудачное
   дерево удаляется best-effort. Если вернуть бэкап не удалось, неудачный
   каталог переименовывается обратно, чтобы установка осталась запускаемой.
7. Helper вызывает best-effort `cleanup_stale(&root, Some(version))` для
   своего корня и завершается с кодом `0`. Собственный каталог версии он не
   удаляет: образ `helper.exe` ещё работает, `apply.log` нужен для
   диагностики. Этот остаток удаляет приложение (см. ниже).

Состояние на диске делает восстановление возобновляемым. Если helper убит
между шагами, следующий `recover_install` продолжает с записанной стадии:
`prepared` без каталога установки возвращает бэкап, `old-renamed`/`new-in-place`
с подтверждённым handshake завершают операцию, без подтверждения — откатывают,
`rolling-back` доводит возврат бэкапа. Если файла состояния нет, recovery
best-effort удаляет осиротевшие `<name>.voxhold-next-*` (копии пользовательских
файлов после падения до записи состояния) и не трогает бэкап. При
неповреждённом или повреждённом состоянии staging-каталог не удаляется.

Приложение после интеграции должно:

* при старте получить корень и вызвать очистку; `updates_root()` возвращает
  `Result<PathBuf>`, поэтому ошибку нужно обработать, а не игнорировать:

  ```rust
  let install_dir = /* каталог установки */;
  let root = voxhold_update::stage::updates_root()?; // Result<PathBuf>
  let outcome = voxhold_update::recovery::recover_install(
      install_dir,
      voxhold_update::recovery::RecoveryMode::Observer,
  )?; // Result<RecoveryOutcome>
  // keep = Some(version), если ready.json готового обновления сохраняется.
  let removed = voxhold_update::stage::cleanup_stale(&root, keep)?; // Result<usize>
  ```

  Observer завершает только доказанную операцию (`completed`) и никогда не
  переименовывает каталоги; незавершённый откат остаётся helper'у
  (`NeedsUpdater`). Приложение использует `cleanup_stale_keeping`, чтобы
  одновременно сохранить каталог текущей версии с `helper.exe`/handshake и
  каталог найденного `ready.json`. Каталог с `handshake.ok` или `helper.exe`
  защищается по содержимому, даже если локальная сборка не передала
  `VOXHOLD_BUILD_VERSION`. `cleanup_stale` остаётся обёрткой над одним `keep`.

  Observer запускается и при старте после обновления, если handshake уже
  записан: файл с id операции — это доказательство запуска. Без него
  (запись не удалась) состояние остаётся `new-in-place`, бэкап сохраняется,
  и helper откатывает операцию. Поэтому нельзя пропускать recovery только
  из-за наличия `--update-handshake`.

  `cleanup_stale` best-effort: занятая запись пропускается, остальные
  удаляются, `Err` — только если не читается сам корень;
* после записи handshake-файла запланировать повторный `cleanup_stale` через
  короткий таймер (несколько секунд). Helper живёт до конца handshake и ещё
  ~1 с удаляет бэкап, поэтому первый проход мог пропустить его каталог с
  `helper.exe`; повторный проход удаляет остаток, когда образ уже не
  удерживается. К этому моменту observer уже перевёл операцию в `completed`
  и удалил бэкап, поэтому удаление handshake-каталога больше не мешает
  восстановлению. Если запись всё ещё занята, она просто пропускается и будет
  удалена при следующем старте;
* завершить звонок и сохранить настройки перед запуском helper;
* передавать helper абсолютные пути и **не передавать `--detached`**: это
  внутренний флаг helper'а для собственного перезапуска;
* при старте с `--update-handshake <file>` записать файл только после
  успешной инициализации;
* повышать права только по явному действию пользователя (helper этого не делает).

## Локальная приёмка A → B

1. `cargo run -p voxhold-release -- keygen --out <вне-репозитория>`.
2. Собрать A командой `pack --dir <stage-A> --version 0.1.0 --out a.zip`,
   затем B той же командой с `--version 0.2.0 --out VoxHold-portable.zip`. Клиент B соберите с
   `VOXHOLD_BUILD_VERSION=0.2.0`, иначе он будет считать себя версией
   `CARGO_PKG_VERSION` и не увидит обновление.
3. `delta --base a.zip --target VoxHold-portable.zip --out VoxHold-delta-0.1.0.zip`.
4. Поднять loopback HTTP-сервер с `VoxHold-portable.zip`, `VoxHold-delta-0.1.0.zip`, `VoxHold-Setup.exe`.
5. `manifest --full VoxHold-portable.zip --setup VoxHold-Setup.exe --version 0.2.0 --delta VoxHold-delta-0.1.0.zip ...
    --base-url http://127.0.0.1:<port>`; без флага используется закреплённый
    GitHub URL канала. База принимает HTTPS и loopback HTTP, остальные адреса
    отклоняются до подписи.
6. `verify --manifest latest.json --sig latest.json.sig --full VoxHold-portable.zip`.
7. В тесте подписать манифест тестовым ключом, получить `VerifiedManifest`
   через `verify_and_parse` и вызвать `stage_update` с распакованным A;
   проверить, что скачалась дельта и `ready.json.method == "delta"`, а
   размер скачанных байт меньше полного пакета. Без базы, с битой дельтой и
   при `delta.size >= full.size` должен быть полный пакет.

HTTP допустим только для loopback; подпись проверяется и в этом режиме.
`VOXHOLD_UPDATE_PUBKEY` позволяет собрать тестовый клиент с другим ключом, но
не отключает проверку.

## CI

Версия берётся из `[package].version` в `Cargo.toml` в формате `X.Y.Z`.
Для следующего выпуска увеличьте её в `Cargo.toml` и `Cargo.lock`.
После релизного PR `dev → main` GitHub Actions автоматически запускает
публикацию при изменении `Cargo.toml`. Для повторной попытки можно
перезапустить упавший job или выбрать **Actions → Release → Run workflow**
на `main` с флагом `publish`. Тег `v<version>` создаёт CI.

Workflow запускает тесты апдейтера и собирает x64-клиент с медиа, helper и
release CLI. В общий комплект входят `Voxhold.exe`, `voxhold-updater.exe`,
`assets/`, лицензии и `package.json`. CI проверяет совпадение файлов Setup и
portable ZIP по SHA-256 и прогоняет замену файлов настоящим helper на обоих
вариантах установки с подтверждением запуска окна. Для PR в `main` и
ручного запуска без `publish` CI использует одноразовый ключ подписи и
сохраняет файлы в Actions artifacts. Для PR в `dev` работает обычный
workflow **Windows**.

При публикации CI проверяет подпись предыдущего версионного релиза и его
ZIP. Он включает дельту, если та меньше полного архива. CI подписывает
манифест, проверяет его встроенным публичным ключом и сравнивает SHA-256
ассетов в GitHub со сборкой. Повтор запуска использует уже опубликованные
байты `v<version>`. Канал `beta` обновляется после публикации этих пакетов.

Для публикации нужен `VOXHOLD_UPDATE_SIGNING_KEY`, соответствующий ключу
из `crates/voxhold-update/update-pubkey.txt`. Опциональные секреты
`WINDOWS_CERT_PFX_BASE64` и `WINDOWS_CERT_PASSWORD` включают Authenticode
для обоих EXE и Setup. Без сертификата остаётся подпись манифеста, а в
манифесте указано `authenticode: false`.

## Ограничения

* MSI и дельта для `Setup.exe` не поддерживаются: установщик скачивается
  целиком, дельта заявлена только для portable ZIP.
* Authenticode без сертификата недоступен: EXE и установщик будут
  неподписанными, SmartScreen может предупредить. Это не заменяет подпись
  манифеста. Клиент проверяет подпись манифеста и SHA-256; Authenticode
  проверяется Windows при запуске, отдельного `WinVerifyTrust` в клиенте нет.
* Схема v1 хранит один публичный ключ; одновременная ротация без выпуска
  клиента не поддерживается.
* `--update-handshake` реализован в `main.rs`: файл пишется после открытия
  окна, ошибка записи видна в рабочей области.
* CI покрывает загрузку манифеста, дельту и полный архив тестами на loopback,
  а запуск и замену файлов Windows — на временной установке. Приёмка `W13`
  включает переход между двумя опубликованными версиями на чистой Windows.
